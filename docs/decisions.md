# Технические решения

Журнал решений с обоснованием — зачем, а не только что. При пересмотре
любого пункта обновляйте запись, а не удаляйте: важно видеть, что уже
пробовали и почему отказались.

## Цветовой фильтр: медианный цвет по региону

Запрошенная формула — «каждый канал считается как сумма(цвет/расстояние)/
количество фото» — реализована **не буквально**. При прямой реализации
(деление на общее число фото, а не на сумму весов) результат почти везде
получается близким к чёрному: `color/distance` при расстояниях в сотни-
тысячи км — это малые доли единицы, а деление ещё и на количество фото
гасит их дальше. Итоговая карта выглядела не «в цветах заката», а тёмной
почти везде — противоречит явной цели запроса.

**Решение:** использовать стандартную интерполяцию обратных расстояний
(IDW, inverse distance weighting) — тот же вес `1/расстояние` на фото, но
цвет ячейки нормируется на **сумму весов**, а не на количество фото:

```
weight_i = 1 / max(distance_km(cell, photo_i), MIN_DISTANCE_KM)
channel  = Σ(color_i * weight_i) / Σ(weight_i)
```

Это гарантирует, что цвет ячейки всегда остаётся в диапазоне цветов
ближайших фото (взвешенное среднее не может выйти за пределы входных
значений), а не улетает к нулю от одного лишь масштаба расстояний в
километрах. `MIN_DISTANCE_KM = 60` — пол на расстояние, чтобы у фото прямо
под ячейкой не было деления на (почти) ноль.

Альфа-канал (прозрачность) — отдельная величина, не часть исходной
формулы: без неё вся карта, включая области без единого фото, была бы
закрашена (пусть и почти чёрным) сплошным слоем. Альфа насыщается по той
же сумме весов через `1 - exp(-Σweight * K)`, где `K` подобран так, что
одно фото на расстоянии ~1500км даёт примерно половину от максимальной
альфы (`ALPHA_HALF_DISTANCE_KM` в `colorFilterLayer.ts`) — вблизи фото
цвет виден отчётливо, далеко от всех фото карта остаётся читаемой.

**Производительность:** цвет считается не на каждый пиксель экрана, а на
сетку 56×36 ячеек, которая затем растягивается на весь canvas с
сглаживанием — визуально выглядит как гладкий градиент, а не мозаика из
крупных квадратов, и пересчёт (перебор всех фото на каждую из ~2000 ячеек)
остаётся дешёвым даже на сотнях фото. Пересчёт происходит на
`moveend`/`zoomend`/`resize`, не на каждый кадр перетаскивания.

Все константы (`GRID_COLS/ROWS`, `MIN_DISTANCE_KM`, `MAX_ALPHA`,
`ALPHA_HALF_DISTANCE_KM`) — в `src/lib/colorFilterLayer.ts`, чисто
эстетический подбор, менять по вкусу без страха что-то сломать
(проверено: `npm run build` не зависит от конкретных значений).

## Карта: Leaflet + OpenStreetMap, а не Google Maps

Google Maps/Earth требует Google Cloud аккаунт, API-ключ и привязку карты к
способу оплаты. Leaflet + OSM — полностью бесплатно, без ключей, ценой
менее «глянцевого» вида тайлов по умолчанию. Для прототипа это был
однозначный выбор пользователя на этапе планирования.

## Карта: 2D, а не 3D-глобус

Запрошено пользователем, оценено как отдельная смена технологии, а не
доработка текущей. Leaflet — принципиально 2D slippy-map библиотека; честный
вращающийся 3D-глобус с кластеризацией фото потребовал бы либо Mapbox GL
(проекция `globe`, но снова нужен аккаунт/токен — тот же компромисс, что и
с Google Maps), либо Three.js-обёртки вроде `react-globe.gl`/CesiumJS — в
обоих случаях: новый рендер-движок, свой слой кластеризации взамен
`react-leaflet-cluster`, другой подход к маркерам. Это самостоятельный
проект, а не правка бага.

**Решение:** остаться на Leaflet, вместо глобуса исправить конкретный баг,
который и был реальной причиной запроса — см. ниже.

## Границы карты

**Проблема:** карту можно было утащить перетаскиванием выше северного
полюса или ниже южного — там либо пустота, либо задвоенные/битые тайлы.

**Причина:** тайлы OSM физически существуют только в пределах проекции Web
Mercator, то есть до широты примерно ±85.0511° — выше/ниже проекция уходит
в бесконечность, а поставщик тайлов такие плитки просто не генерирует.

**Решение:** `LeafletMapView.tsx` задаёт
`maxBounds={[[-85.0511, -Infinity], [85.0511, Infinity]]}` и
`maxBoundsViscosity={1.0}`. Широта зажата на границе проекции, долгота
оставлена не ограниченной (`Infinity` с обеих сторон), чтобы не сломать
`worldCopyJump` — бесконечную горизонтальную прокрутку карты по долготе.
`maxBoundsViscosity={1.0}` делает границу «твёрдой»: карту невозможно
утащить за предел даже временно (без него граница пружинит, но
перетащить за неё на мгновение всё равно можно).

## Пустая мини-карта

**Проблема:** мини-карта в форме «Add sunset» открывалась пустой — без
тайлов.

**Причина:** Leaflet измеряет размер своего контейнера один раз, в момент
создания карты. Внутри модалки, которая только что появилась в DOM
(особенно с учётом того, что `AddSunsetForm` подгружается отдельным чанком
через `next/dynamic`), браузер не всегда успевает завершить layout к этому
моменту — Leaflet может замерить контейнер как 0×0 и больше не
пересчитывать размер сам.

**Решение:** `MiniLocationPicker.tsx` рендерит служебный компонент
`SizeFixer`, который на следующий кадр после монтирования вызывает
`map.invalidateSize()`. Это стандартный, задокументированный в экосистеме
Leaflet приём для карт внутри модалок/табов/аккордеонов.

Заодно исправлен UX по умолчанию: карта форму открывалась в точке
`(20, 0)` (Гвинейский залив) без всякой попытки определить локацию
пользователя. Теперь `MiniLocationPicker` при монтировании один раз тихо
пробует `navigator.geolocation`; при отказе/ошибке/таймауте остаётся
дефолт — **Париж** (`48.8566, 2.3522`), без сообщения об ошибке (ошибка
показывается только при явном клике на кнопку «Use my location»).

## Долгота за пределами ±180 после перетаскивания мини-карты

**Проблема:** загрузка фото падала с ошибкой `invalid lng`, хотя пользователь
просто выбирал точку на мини-карте формы «Add sunset».

**Причина:** `L.Map.getCenter()` в Leaflet не оборачивает (`wrap`) долготу
обратно в диапазон [-180, 180] — при зуме мини-карты далеко и перетаскивании
через антимеридиан центр может улететь, например, до 188° вместо -172°.
`CenterTracker` в `MiniLocationPicker.tsx` передавал это значение как есть,
а серверная валидация в `POST /api/sunsets` (`lng < -180 || lng > 180`)
честно его отклоняла.

**Решение:** двойная защита:
1. Клиент: `e.target.getCenter().wrap()` в `CenterTracker` — долгота
   нормализуется сразу после каждого `moveend`, до того как попасть в
   состояние формы. Заодно на мини-карту добавлены те же `maxBounds`, что
   и на основной карте (широта ±85.0511°), для единообразия.
2. Сервер: `POST /api/sunsets` больше не отклоняет долготу вне ±180, а
   нормализует её формулой `((lng % 360) + 540) % 360 - 180`
   (`normalizeLng()` в `api/sunsets/route.ts`) — защита на случай, если
   когда-нибудь появится другой клиент (не эта форма), который тоже
   пришлёт незавёрнутое значение. Широта по-прежнему строго отклоняется вне
   [-90, 90] — для неё нет понятия «заворачивания», выход за диапазон
   всегда означает ошибку, а не побочный эффект панорамирования.

Проверено вручную через headless-браузер: зум мини-карты до предела,
десятки перетаскиваний в одну сторону до пересечения антимеридиана —
отображаемые координаты корректно остаются в диапазоне, форма отправляется
без ошибки.

## База данных: SQLite, а не Postgres

Prisma не даёт переключать `provider` датасорса через переменную окружения
(только `url`) — значит, SQLite для разработки и Postgres в проде означали
бы две отдельные Prisma-схемы и две ветки миграций. Вместо этого выбран
SQLite и локально, и в проде: файл БД лежит на том же Railway Volume, что
и фото. Осознанный компромисс — сервис должен оставаться в одном инстансе
(без горизонтального масштабирования), но это и так требование самого
Volume под фото, так что новых ограничений это не добавляет на масштабе
прототипа.

## Prisma: 6.19.3, а не «latest»

На момент разработки `npm install prisma@latest` устанавливал `8.0.0-rc.13`
— релиз-кандидат, у которого сломан граф зависимостей внутри
`@prisma/composer-cli` (`ETARGET` на пакете `effect`), и который потребовал
бы использовать driver adapters и `prisma.config.ts` вместо привычного
`datasource { url = env("DATABASE_URL") }` в `schema.prisma`. Для прототипа
это лишняя нестабильность. Закреплена последняя релизная версия ветки 6.x
(`6.19.3`), работающая по классической схеме без driver adapters.

**Если апгрейдить Prisma в будущем:** сначала проверить, вышла ли
стабильная (не `-rc.`) версия 7+, и оценить объём миграции на driver
adapters отдельно — это не просто бамп версии.

## Рендер карты и SSR (`ssr: false`)

Импорт `leaflet` обращается к `window` уже на уровне модуля — при попытке
Next.js прогенерировать статическую версию главной страницы на сервере
сборка падала с `ReferenceError: window is not defined`. Все компоненты,
которые (прямо или через цепочку импортов) тянут `leaflet`/`react-leaflet`,
должны подключаться через `next/dynamic(() => import(...), { ssr: false })`
— см. [architecture.md](architecture.md#рендеринг-карты-и-ssr) за списком
таких компонентов и объяснением, почему это одна точка, о которой легко
забыть при добавлении нового компонента с картой.

## Хранилище фото: файловая система на Railway Volume, а не S3/R2

Отдельного объектного хранилища (S3-совместимого) не подключали — Railway
Volume, который в любом случае нужен под SQLite, вполне годится и под фото
на масштабе прототипа. Если сервис вырастет за пределы одного инстанса,
это первое, что стоит вынести (вместе с переходом на Postgres).

## Геокодирование: публичный Nominatim, а не свой инстанс

По [политике использования Nominatim](https://operations.osmfoundation.org/policies/nominatim/)
публичный эндпоинт допускает не более 1 запроса в секунду и требует
валидный `User-Agent`. Обратное геокодирование в проекте происходит один
раз на загрузку фото (не массово/по сетке), что укладывается в политику на
объёме прототипа. `NOMINATIM_USER_AGENT` обязателен в env — без него
`geocode.ts` пропускает запрос и возвращает `null`, не блокируя загрузку.
При реальном росте нагрузки — поднимать собственный инстанс Nominatim.

## Авторизация модерации: подписанная cookie, а не сессии в БД

Единственная защищённая страница (`/preadmin`) с одним общим паролем из
env — полноценная система сессий избыточна. Вместо неё —
HMAC-подписанный токен `expiry.signature` в cookie
(`lib/auth.ts`), проверяемый без обращения к БД. Пароль и подпись
сравниваются через `crypto.timingSafeEqual`.

## Собственный git-репозиторий для `worldofsunsets`

Каталог проекта изначально лежал внутри чужого родительского
git-репозитория, где также хранились `credentials.env` и другие личные
файлы, не относящиеся к проекту. Чтобы не рисковать случайной утечкой этих
файлов при пуше на GitHub/Railway, для `worldofsunsets` инициализирован
отдельный, самостоятельный git-репозиторий (`git init` прямо в каталоге
проекта), не связанный с родительским.
